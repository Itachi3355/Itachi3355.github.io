    how I think

    Ideas I keep coming back to

    Tools change every year. These ideas don't, and each one shows up in something I've built.

    A defense only counts if it survives an attacker who adapts.

    A guard tested against a fixed list of attacks gives false confidence. Real attackers change tactics once they see the guard, so that is the test I run.

    seen in prompt-injection research

    Every claim should trace back to a source.

    AI output is easy to believe and hard to check. I build tools that sort each claim into verified, inferred, speculative or unverifiable, so people know what still needs checking.

    seen in verify-ai-output the eval step in the console

    Anything an agent reads is untrusted input.

    Web pages, documents and tool results can all carry hidden instructions. Content should be able to inform an agent but never command it.

    seen in prompt-injection-audit the guard in the pipeline

    Give an agent only the power the task needs.

    An agent that can do everything will eventually do the wrong thing. I scope what each agent may do, then test that the limits actually hold.

    seen in cua-capability-system

    research · ai security · mcp

    When an agent reads tool results, what does a defense actually cost?

    mcp-injection-eval

    A reproducible harness for indirect prompt injection at an MCP-style tool boundary: 20 attacks hidden in tool results, each with a programmatic success check, run against four defense modes and scored on attack success and utility under attack. Main finding: the cost comes from judge granularity, not detection. Filtering per item instead of per result kept attack success at 0% and raised utility from 5% to 100%. The undefended model also refused all 20 attacks, and the write-up reports that as a floor effect, not a win.

    utility under attack 5% → 100% at 0% attack success github.com/Itachi3355/mcp-injection-eval ↗
